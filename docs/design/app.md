# The app

How the Next.js frontend talks to the backend and shows an answer, its evidence and the other pages. Each choice says what was picked and why, with the issue and the evidence. The short version is under "Key design choices" in [Architecture](../architecture.md#key-design-choices).

## Talking to the backend

- **The browser calls the backend directly, with CORS**, rather than through a Next.js proxy, because streaming the chat is simpler without a proxy that buffers the response (#50).
- **The chat reads `POST /chat` with `fetch` and a small SSE parser, not `EventSource`**, because `EventSource` can only send a GET. The conversation lives in the page's state and is sent with each question, cut to the backend's limits (`frontend/lib/chat-limits.ts` mirrors `schemas/chat.py`); Stop aborts the request and keeps what has arrived. An `error` event, a 503 or a lost connection shows a readable message with a retry. The disclaimer sits under the question box so it stays in view while the answer scrolls, so it moved out of the shared layout into each page (#19).
- **The drugs page asks the backend only when its own list has no match.** The list filters on scope names and aliases. `GET /drugs/resolve` also knows salt names and PubChem synonyms, so "imatinib mesylate" shows as supported under another name instead of "not supported", and a typo gets the closest names. A suggestion is a link the user clicks, never applied on its own, because look-alike names (Celexa, Celebrex) make a silent correction unsafe (#79). From four letters on, names that start with the input are suggested first, shortest first, then the closest spellings, three at most (`CompoundService._suggest`): "novamin" finds Novaminsulfon, which the 0.8 spelling cutoff misses (ratio 0.70), and "amox" puts Amoxil before Diamox, a different drug (#189). In the chat the same suggestions become buttons under the answer, "Did you mean Novaminsulfon (metamizole)?", that ask the question again with the name replaced, every whole-word occurrence in any case, or ask about the suggested name alone when the question spells it differently from the tool call (`frontend/lib/did-you-mean.ts`, #189).

## The chat

- **The chat follows the answer like a terminal** (`frontend/lib/use-follow-answer.ts`, #179). The chat scrolls in its own area from the header to the bottom of the window, not the window itself (#296): the question box floats over the bottom of that area with a short fade above it, so the scrollbar runs the whole height beside it (the owner found it awkward that it stopped above the box). The box is `sticky` inside the area rather than laid over it, so the end of the last answer always stops above it. Sending a question scrolls the area to its end; scrolling an element into view instead would leave the question box over the end of the conversation. Opening a saved chat does the same, so it starts at its newest message, which is the answer the panel and the navigator show (the owner's call, #311); it used to open at its top, beside the panel's newest answer. While the answer streams in, a `ResizeObserver` on the conversation keeps the area at its end, and once more when it ends, because the answer's pills and usage line appear with the end. Scrolling up stops that, and scrolling back to within 48 px of the end starts it again. The chat's and the panel's scrollbars are thin and rounded (`thin-scrollbar` in `globals.css`), and the chat's shows only while the pointer is over it. Print lets the area grow to its content, so the whole conversation is printed (#244). Following used to stop once the newest turn showed a 3D view, which sat above the answer and would have been pushed off screen; since the view moved into the evidence panel (#303), nothing above the answer grows and following never stops for it.
- **The evidence behind an answer sits in a panel beside the chat** (`components/evidence-panel.tsx`, `lib/evidence.ts`, #303, part of #295). A turn in the chat shows its question, then one live line with the current step while the answer comes in, then pills ("✓ 4 steps", "5 sources", "3D · 2HYY" or a dimmed "no 3D") that open the panel's tab for that answer; the answer, its source-check badge, the did-you-mean buttons and the usage line stay in the chat. The panel (440 px, screens 900 px and wider) shows one answer at a time, "Answer 2 of 3" with ‹ ›, and four tabs: 3D (the answer's view, a switch between its drugs when it looked up several, and "Structures in this chat" across answers), Sources (numbered cards with the passage, the label's date and its DailyMed link, then the openFDA credit; these replace the "Based on" / "Also from" rows under the answer), Steps, and Flow (the answer's own path through the guide's diagram, #347). A citation chip still shows its popover on hover; a click opens Sources on that answer with the cited passages highlighted. Under 900 px the panel is a sheet from the bottom. It shows the newest answer, a sent question opens on Steps, and an opened answer on its 3D view, else its sources. As the reader scrolls, it shows the turn whose top is above 40% of the chat's scroll area, or the last turn at the end of the chat, where a short last answer never reaches that line; that turn gets the orange line and status light in the chat (`lib/read-turn.ts`, #304). Only the reader's scrolling counts: `useFollowAnswer` remembers where its own scrolls put the chat, and a scroll event that lands anywhere else is the reader's, so the chat following a live answer never moves the panel, nor does it take the panel back from an earlier answer the reader opened from its pills. The other way round, stepping with ‹ › or picking from "Structures in this chat" scrolls the chat to that turn's top, as one of the page's own moves (the owner noticed the arrows didn't scroll). On phones the sheet covers the chat, so there it opens only from the pills and chips. Its scroll lock used to move the page's scroll position to `<body>` while it was open, so scrolling on a phone didn't change the turn it shows; since the chat scrolls in its own area (#296), the lock no longer touches it, and the turn follows the reader on phones too. When a live answer's structure arrives while the panel shows that answer, the 3D tab opens by itself, once per question, with a dot until the reader picks a tab; if the reader was elsewhere, it opens when they come back. While the panel shows another answer, a "● Live answer" button goes back to the live one and to the end of the chat, where following starts again. The prototype went to the top of the live turn instead; the end is where the answer is being written. The owner picked this layout ("D") in the redesign prototypes on 2026-10-19 (`docs/spikes/redesign-2026-10/d.html`), after asking how it plays out over several questions. Print hides the panel and prints each answer's numbered sources under it instead (#309).
- **A question navigator sits on the chat's right edge** (`components/question-navigator.tsx`, #296), because the owner asked for scroll marks "like Grok's dashes" and it is in the picked prototype (`docs/spikes/redesign-2026-10/d.html`). It shows once a chat has two questions, one dash each; the turn the panel shows gets a long orange dash with its number, and the live answer's dash pulses (not with reduced motion). Hovering shows every number and a list of the questions; a dash or a list entry scrolls the chat to that question's top and opens its answer in the panel, keeping the tab the reader had if the panel already showed it. Phones keep only the dashes, without numbers or the list, and a dash there scrolls the chat without opening the sheet, which would cover the question just jumped to.
- **Citations become named chips, one per run of citations** (`components/citation-chip.tsx`, #160). Once the `sources` event arrives, `[2][3]`, `[1, 4]` or `【1】` becomes one pill naming the first source it cites ("Gleevec · Warnings and cautions", or a PubChem, ChEMBL or RCSB page, which carry a number too since #209), with "+1" for each other source. Its popover lists every source behind it: a passage with the excerpt from the `search_labels` result, the label date and the DailyMed link, a page with its link. Named chips were the owner's pick over bare numbers, because they say where a fact comes from without hovering; grouping keeps the text calm, since gpt-oss-20b often cites two passages per sentence (11 of 11 bullets in the imatinib warnings answer). A number that points at no passage is left out instead of shown as text: in the recorded sildenafil answer, `【1】` pointed at a ChEMBL target, which had no number then. Under the answer, PubChem, ChEMBL and RCSB pages were listed as links, and when an answer read labels but cited none of their passages, a "Based on" line named those labels: the recorded ibuprofen vs naproxen answer read 10 passages and cited none. Since #303 the evidence panel's Sources tab lists every source instead, cited or not. An answer that used label text credits "Data provided by the U.S. Food and Drug Administration (openFDA)", openFDA linked to open.fda.gov: the credit openFDA's [terms](https://open.fda.gov/terms/) ask for, though they don't require it. The frontend decides it from the sources: the credit shows when one of them is a DailyMed label passage (#180).
- **Tool results open from the progress steps** (`components/progress-steps.tsx`, `components/tool-cards/`, #161). The backend sends each `tool_call` right after the step that announces it, so a step keeps its call and, once the `tool_result` arrives, opens into what the tool returned. A step with a result looks like any other step, a mark and its text, with a short summary ("5 passages") on the line under it (the owner asked for the second line once the steps moved into the narrower evidence panel, where the summary often wrapped on its own), so every tool call reads the same; the owner asked for this after seeing bordered cards in the list. It opens into the drug a name matched, PubChem's properties, ChEMBL's targets, the complex's hydrogen bonds and closest residues, or every passage a label search found with the cited ones marked. `lib/tool-cards.ts` turns each raw result into a typed card, including `not_supported` with the closest names, `invalid_arguments` and `no_complex`. The owner picked this over a separate "Looked up" block under the answer and over cards above it, after a mockup with real results: nothing shows twice, and the answer stays first. Properties fetched drug by drug, as gpt-oss-20b did in the recorded ibuprofen vs naproxen answer (two `get_properties` calls, no `compare_drugs`), merge into one side-by-side table once the answer is done; merging only then keeps the list from jumping while it streams. A stand-in complex's caption opens its card, because it says what the structure really shows. Long lists stop at 8 residues and 6 genes with a "Show all" (metformin's complex I lists 50 genes). "View in 3D" opens the drug's 3D view (#21), and suggested names are plain text, not links. Since #303 the steps are the evidence panel's Steps tab instead of a list above the answer, so they no longer fold away into "4 steps" when the answer is done; the turn's "steps" pill opens the tab, and a done step shows a tick.
- **A label search explains itself in its step on the Steps tab, not in a tab of its own** (#41). The `retrieval_trace` event joins its `search_labels` step (`withTrace` in `frontend/lib/chat-turn.ts`), and the step's card (`components/tool-cards/labels-card.tsx`) shows what the search was narrowed to (drugs with their generic name and label count, who chose the filter, the section groups, the product type), the ranking used, and every candidate as a ranked row with its similarity, kept or dropped, its `[n]` and whether the answer cites it. The card already listed the passages, so a separate tab would have listed them twice; picked from three mockups on recorded gpt-oss-20b chats. The rank isn't the similarity order: in dense mode a chunk in the asked-for section counts `RETRIEVAL_SECTION_GROUP_BOOST` (0.15) higher, so "Does ibuprofen interact with warfarin?" ranks the interaction passages (0.52, 0.50) above nursing mothers (0.64); the bar draws the bonus as a light end, and the trace carries `mode`, `min_score` and `section_group_boost` for it. In hybrid mode each row shows its embedding and keyword ranks instead. Query translation always shows as skipped, since #114 measured it and didn't build it. Chats saved before the trace was kept show the old passage list.
- **The source check shows as a badge under the answer and underlines in it** (`components/source-check-badge.tsx`, `components/unbacked-mark.tsx`, #214). Once the answer has streamed, a badge says "Checking the answer against the sources…" (the guard's status event) beside a turning orange ring, then shows a green shield ("every fact is backed by the source it cites"), turns amber (how many facts are backed, how many sentences aren't) or shows a grey shield ("Not checked against the sources") when the check failed (the colours since #294); an answer with no drug facts gets none. Each sentence the sources don't back gets a dotted amber underline whose popover says "Not backed by the sources" and the check's reason; the source chips stay outside it, and a list item is marked without the heading the splitter puts in front of it. The owner picked marks plus a summary over either alone, so a clean pass shows too, and the badge over a grey line, because the check should be easy to see. "Not backed" rather than "wrong" or "unverified", because most of what the check catches is true but uncited ([source check eval](../evals/source-check-2026-10-14.md)). Against the hand labels of the eval set, 70 of the 79 claims the check rejects at medium effort are unsupported; 6 of the other 9 say what a label doesn't cover, which the labels don't count as drug facts, and 3 are supported. In the live chat the check also caught a false "the label passages don't compare it with Valium" in an answer that had cited that comparison. The frontend finds each claim in the answer line by line with any whitespace (`lib/source-check.ts`): `sourceCheckMarks` finds all 181 claims in their 65 recorded answers, so the event needs no offsets.
- **A fact another returned result holds is shown as backed, with a chip for that result, not underlined** (`lib/remark-source-check.ts`, #220). The check sees every result the answer's tools returned and says `held_elsewhere` with the refs that hold the claim; the badge counts it as backed ("Every fact is in Molecula's sources"), and the amber popover now reads "Not in Molecula's sources". At medium effort on the 181 hand-labelled claims, amber marks fell from 79 to 51 and 54 in two runs, 18 or 20 of the 31 citation misses got a chip for a result the labels name, and 36 of 47 additions stay underlined against 40 before. The owner took that trade. gpt-oss-20b also keeps underlining sentences that state plainly what a label hedges, whatever the prompt says; a stronger checker was #215, closed as not planned ([source check eval](../evals/source-check-2026-10-14.md#judged-against-every-returned-result-220)).
- **Answers render as Markdown with `react-markdown` and `remark-gfm`**, because the chat models write bold, lists and tables (gpt-oss-20b answered both list and table questions in the manual check with them). Raw HTML in an answer shows as text, never as markup: the answer is model output that can quote untrusted label text, and `react-markdown` without `rehype-raw` already does this, which a test holds in place. Links open in a new tab with `rel="noopener noreferrer"`, and citations stay as written while the answer streams. A half-streamed `**` shows as written until it closes (`components/answer-markdown.tsx`, #151).
- **Conversations are kept in the browser's IndexedDB and listed in a sidebar** (`lib/chat-history.ts`, `lib/chat-history-indexeddb.ts`, `components/chat-sidebar.tsx`, #243). Not `localStorage`: one label answer with its tool results is about 30 KB, and its ~5 MB per site would hold about 150 answers. Not on the server: medical questions are sensitive, so no question or answer text is stored there, and without the login there are no accounts to keep a history apart. A conversation is saved with its turns as the chat holds them (answer, steps, tool results, sources, source check) when an answer starts and when it ends. A reload lists the chats and opens an empty one, and an answer that was streaming reopens as stopped. If IndexedDB is missing or refuses (a private window, full storage), the chat says history is off and works without it. Collapsed, the sidebar is a 56 px rail of icons beside the centred chat column, expanded it lists the chats by day, and on a phone it is a drawer opened from ☰; the owner picked this layout from a mockup (option B), and whether the rail is expanded is kept in `localStorage`. Bookmarks are an ordered list of chat ids in a second IndexedDB store next to the chats (database version 2; the upgrade only adds the store, so chats saved before stay), and a deleted chat loses its bookmark. They sit in a "Bookmarked" group above the days, and the rail shows the first five as numbered buttons with the rest behind "+N"; removing one shows Undo for 6 seconds instead of a confirm (variant B2, #247).
- **An answer keeps streaming when another chat is opened, and one answer runs at a time** (`lib/use-conversations.ts`, #250). The stream belongs to its chat, not to the one on screen, so people can read earlier chats while the model works; the sidebar row shows a spinner, and on the rail the chat's bookmark number does, or the Chat history button when the chat has no number. A question asked in another chat meanwhile waits in line as a queued turn ("Waiting for the answer in another chat to finish…") and starts when the answers before it end, oldest first. The owner chose waiting over refusing the question. Not in parallel: the local model serves one request at a time (LM Studio `--parallel 1`), and parallel answers would double the cloud cost. An answer counts as ended at its `done` or `error` event, so the next one doesn't wait for the connection to close. Stop or deleting the chat ends an answer or takes its question out of the line. A reload still ends everything, and a queued question reopens as stopped.
- **The open conversation is exported in the browser, as JSON, CSV or a printed page** (`lib/conversation-export.ts`, `components/export-menu.tsx`, #244). JSON holds every turn as the chat keeps it, tool results and sources included; CSV has one row per message (time, role, text, sources as `[n] drug – section – url`, by the numbers the answer cites), RFC 4180 quoting, CRLF rows and a byte order mark so Excel reads it as UTF-8, and a cell that starts like a formula gets a leading `'` because answers can quote untrusted label text. PDF goes through the browser's print dialog; no PDF library, so nothing is added to the bundle. The printed conversation is its own design in the instrument look (#309), not the screen with parts hidden: the `@media print` section of `app/globals.css` lays it out on the full width of the paper in point sizes, and `components/printed-conversation.tsx` adds what only paper shows. The first page starts with Molecula, the number of questions, the print date and a fine ruler, then the chat's title if it was renamed (otherwise the title is the first question, which follows); each turn opens with a rule and its orange `Q-01 · Query` label, with the time it was asked on the right, then the question as a heading, the answer, the source check as a line of text, and the answer's sources in a small table (number, drug and section or site and name, link); the disclaimer and one openFDA credit close the conversation, and in Chrome, which supports `@page` margin boxes, the page margin carries "Molecula" and the page number. Citation chips print as the numbers of that table, such as `[2, 3]`. Browsers leave out backgrounds when printing unless the dialog's "Background graphics" is on, so colour comes only from text, borders and SVG: the orange light in the head is an SVG circle, not a filled box. A question and its label stay with the start of the answer (`break-after: avoid`), and list items, table rows and source lines don't split, but a turn as a whole may run onto the next page. #261 had kept every turn off a page break, which pushed a long answer to the next page and left a gap at the end of the page before it; #261's "You" / "Molecula" labels gave way to the `Q-01` label the screen already shows. An answer that showed a drug in 3D prints a still picture of it between the answer and its sources, with the drug, the target and the PDB ID beside it and the colour legend under it, its swatches drawn in SVG (`PrintedStructure`, #312). "Print or save as PDF" first draws each structure of the conversation off screen as the evidence panel first shows it (the binding site, or the molecule alone), in the light colours whatever the screen shows, and exports it with 3Dmol's `pngURI()` (`components/structure/picture.ts`). The views are drawn one after the other and each is closed before the next, because browsers keep only a few live WebGL contexts per page; the dialog opens once every picture is on the page and decoded (`lib/use-printed-pictures.ts`), and the menu item reads "Preparing the 3D pictures…" meanwhile. In the owner's Chrome five structures took 0.3 s in all. A picture that fails, or takes more than 20 s, prints a line saying so instead of holding back the print. Ctrl+P can't be held back, since the browser doesn't wait for anything after `beforeprint`, and drawing every structure ahead, when it arrives or when a chat is opened, would spend WebGL work on prints that mostly never come; so Ctrl+P prints the pictures the menu drew before (a drug's picture is kept while the chat page is open) and, for the rest, a line pointing to the menu. The chat model isn't printed: a turn doesn't record which model answered it, and a saved chat may have been answered by another model than the one running now. Dark mode applies on screen only, so a page printed from a dark browser comes out dark on white. Turns now carry `askedAt` and `answeredAt` for the CSV time; chats saved before have none and export with an empty time.
- **A link to the chat opens a fresh chat; Back finds the old one.** `cacheComponents` makes Next.js keep a page hidden in React's `<Activity>` when another one opens and show the same instance on the next visit, so New chat or a saved chat picked on the dashboard showed the chat from before. `LinkedChat` keys the chat on `useRouter().bfcacheId`, which changes on every link and stays the same on Back and Forward (`frontend/app/linked-chat.tsx`, #392). Effects run again each time a hidden page shows, so `useConversations` asks a linked question again only when leaving stopped its answer before it ended, in the chat it was first asked in (#395).

## The other pages

- **The app shows how to connect an MCP client, from the setup doc's own text.** "MCP server" sits at the foot of the desktop sidebar and its rail, with Settings and the language switch (#376), and opens a dialog with what the six tools return, the Claude Desktop config and the start commands, each with a copy button (`frontend/components/mcp-dialog.tsx`). The config and commands are kept as strings in that file, and `mcp-dialog.test.tsx` reads `docs/setup.md` and fails when one is missing from it, so the two can't drift apart. The phone drawer leaves it out: connecting an assistant needs a checkout on a computer. The dialog says the server runs only next to the user's checkout: it has no auth and answers only localhost (#301).
- **The benchmark page reads a committed results file per benchmark** (`app/benchmarks/`, `components/benchmarks/`, #274). Its one backend call, `GET /retrieval`, only marks the model the instance embeds with, and the page works without it (#350). `/benchmarks` imports `frontend/lib/benchmarks/embeddings-2026-10-12.json` (#273) at build time, so it shows how the embedding model was chosen without the store, a model or the network. The question × model hit grid is the entry point, with the question or model it opens beside it (a full-screen sheet on a phone), then the recall@k curves, the costs and how it was measured: the owner's pick of three mockups. Each benchmark is one entry in `components/benchmarks/registry.tsx`, so another eval is added as one more entry with its own file and components. The second entry, and the first the page opens on, is the chat-model benchmark (#404): `evals/chat_model/benchmark_export.py` writes `chat-models-2026-10-22.json` from the from-memory and comparisons caches of the five runs at medium and their hand verdicts, computing every count from the answers. The page shows a table per model for both evals with the two defaults marked and the local GPU named, then every answer as a dot under its question (grey with no flag, red when it adds a fact from memory, blue when it denies data the store has, an empty ring when it failed), and beside it the answer, the tools it called and the verdict's note: the owner's pick of three mockups. Red and blue were checked to stay apart for every kind of colour blindness in both themes, and a flag never rests on colour alone: the table counts it and the answer names it. Both entries draw their marks from one module (`components/benchmarks/dots.tsx`), so the embedding hit grid marks each question × model with a dot too, and both use thin rules instead of rounded boxes and the same underline tabs (`tab-switch.tsx`, #407). The rank is an orange ramp, the owner's pick of three mockups over grey hits with red misses and the old blue ramp, because the site's colour is orange: its three steps differ in lightness alone, so they hold for every kind of colour blindness, and a miss is an empty ring. A light orange tint marks the app's model, down its column, and the question being read, across its row. The page keeps the chat sidebar, with a Benchmarks link in it (the owner's call): a chat picked there opens in the chat through `/?chat=<id>` (`savedChatLink`).
- **The dashboard reads `GET /stats` and draws its charts itself, in SVG** (`app/dashboard/`, `components/dashboard/`, #335), like the benchmark charts, so it adds no chart library. The owner picked the layout from three mockups: what the store holds first, then five usage numbers (requests, share answered, typical wait, tokens, cost), then requests per day by outcome, p50/p95 time to answer, tool calls, how the guard sorted the questions, errors and tokens per day. The range picker asks for 7, 30, 90 or 365 days, and the old numbers stay, dimmed, until the new range arrives. Cost is a number, not a chart, while it is $0, which it always is on a local model; a cost per day chart appears once a cloud model reports one. An empty usage log shows one "no chat requests" box instead of the numbers and charts. Every chart has a table of the same numbers behind a button, and its colours were checked for colour blindness against the card in both themes; a legend and the table mean no value rests on colour alone. "Typical wait" is the median of the daily p50s, since `/stats` sends no single median for the range. The knowledge-base card shows when the labels were fetched (`labels_fetched_to`), which moves when they are fetched again, and the last label update with its date and outcome (`label_update` in `/stats`). With `LABEL_UPDATE_BUTTON=1` it has an Update now button; while a run goes, from the button or the nightly schedule, the card says so and the page asks `/stats` again every 5 s until it ends, since re-embedding changed labels on a CPU takes minutes (#342).
- **How Molecula answers gets a guide page with a fixed example, and each answer its own flow** (#327). The owner picked both, linked, from three mockups (a guide only, a flow per answer only, both linked). `/how-it-answers` (`components/answer-flow/`, #346) follows "Does ibuprofen interact with warfarin?" through the input check, the chat model's `search_labels` call, the drug filter, the embedder's scoring, the +0.15 section bonus, the answer, the canary watch and the source check, each step tagged chat model, embedder or code, with the recorded run's bars and the boost table from `docs/evals/chat-model-filters-2026-10-12.md`. A fixed example because the guide has to work without a model run and show the case the bonus was made for. The Flow tab of the evidence panel (#347) draws the same steps for the open answer: `turnFlow` in `lib/turn-flow.ts` builds them from the turn's own events (the status lines, the tool calls, each search's `retrieval_trace`, the answer's citations and the `source_check`), groups each lookup's steps under the line that announced it ("Search 1 of 2" when there are several), shows a tool other than `search_labels` as the call and one store lookup by code with what it found, adds a "Show it in 3D" step by code after a `get_complex` lookup (the 3D tab loads the stored structure from the backend and the browser draws it; the guide has no step for it, so it has no guide link), and marks steps skipped, waiting, stopped or not reached; each step links to its anchor on the guide. The tab numbers the steps 1 to n in the order the answer ran them, not by the guide's numbers: the guide is an overview of one example, and an answer that took another path (a 3D lookup, two searches) would otherwise jump from 4 to 6. To tell a refused question and a withdrawn answer apart from the rest, the turn now keeps the `category` from `done` and a `replaced` flag from `replace_answer`, both events the chat already sent. The steps are data in `lib/answer-flow.ts`, with a long text for the guide and a short one for the tab, so their wording is checked against the backend in one place. Both are drawn like the Steps tab, a mark and a thin rule rather than boxed cards (`components/answer-flow/flow-line.tsx`), so they keep the instrument look. On the guide the input check's tag says chat model, as in the recorded offline run, and the text says Jev does it online; on the Flow tab it says "Jev or chat model", since no chat event names the model that sorted the question, and so does the extra call that reads the drugs from the question when the chat model named none.

## Look and language

- **Interactive parts come from shadcn/ui on Base UI** (`frontend/components/ui/`, `components.json`): dialogs now, popovers and collapsibles for the source chips and tool cards (#20), because focus, Escape, outside clicks, touch and screen-reader support are where hand-built UI breaks. shadcn copies each component's source into the repo, so it is restyled like our own code. Base UI is shadcn's default since v4 and the successor to Radix from the same authors. The theme is CSS variables in `app/globals.css`, pointed at the app's own colour tokens (#294), and dark mode keeps following the system setting instead of shadcn's `.dark` class. The shadcn CLI and its CSS are dev dependencies; the standalone build ships none of them. The help guide was the first user (#158); it now opens as a sheet from the right, from the ? icon in the chat header, over a clear backdrop so the chat beside it stays readable (#376).
- **The app has an "instrument" look: warm grey surfaces, one signal orange, Inter Tight and JetBrains Mono** (`frontend/app/globals.css`, `app/layout.tsx`, #294). The owner picked it from clickable prototypes of eleven directions on 2026-10-19 and 2026-10-20 ("J2 · Instrument, calmer", kept in `docs/spikes/redesign-2026-10/`): the zinc defaults looked unfinished, and glass and glow looked cheap. Colours are named tokens (`page`, `panel`, `card`, `ink` to `ink-3`, `rule`, `rule-2`, `signal`, `ok`) set once for light and once for dark, so a component names one class instead of a light and a dark shade, and the shadcn tokens point at them. Contrast stays soft, with no pure black or white; the light page is a notch darker than the prototype's because the owner found that too bright.
