# Agent, models and tools

How the backend is structured, which models answer, and how the agent calls tools, cites and streams. Each choice says what was picked and why, with the issue and the evidence. The short version is under "Key design choices" in [Architecture](../architecture.md#key-design-choices).

## Code structure

- **One service layer for routes, tools and MCP.** All three are thin wrappers over the same functions, so they answer the same way and none reaches a source (#9, `docs/data-plan.md` §4). Each service is built once at startup and handed to routes as a FastAPI dependency, so tests replace it (#56). The label search (`FilterExtractor`, `LabelRetriever` in `rag/`) is the service behind `search_labels`, so tools may import `rag/` too; a pass-through service would add nothing (#108).
- **One setup module builds the app's parts, for the web app and the MCP server** (`wiring.py`, #420). `main.py` holds the FastAPI app, its routes and `lifespan`, which fills `app.state` from `open_chat` and the other `open_*` factories. The MCP server (`python -m molecula.mcp`) builds its tools with the same `agent_tools`, so it never imports `main.py` and builds no FastAPI app. It serves tools, not a chat, so it shares the tool building and not the guard. The guarded chat is put together in one function, `guarded_chat`, for the default chat and for each model a user picks. `schemas/` imports nothing above itself: the control-character rule the chat schema checks lives in `schemas/text.py`, not in the guard.
- **Prompts are `.md` files with a strict loader** (`prompts/loader.py`, #65). `{name}` is a placeholder, `{{` `}}` are literal braces, and anything else in braces fails, so a typo like `{ today }` or raw JSON can't pass silently. Values are inserted without being parsed again, so label text with braces is safe. Tool docstrings are the only LLM-facing text in Python, because LangChain reads them from there.
- **Typed end to end.** Pydantic models at every boundary: source responses (a wrong shape raises `SourceFormatError`, not a `KeyError`), schemas shared by routes, tools and MCP, and settings. The frontend has a typed client in `frontend/lib/api.ts`.
- **Tests never touch the network.** Source clients run against responses recorded from the live APIs in `tests/fixtures/` (the one hand-edited file has "handmade" in its name), `MockTransport` and a fake clock test retries and rate limits without waiting, and agent tests use a scripted fake chat model (`tests/fake_llm.py`). Real-model checks belong in `backend/evals/`, run with `OFFLINE=1`.

## Models

- **One LLM factory, `ChatOpenAI` against any OpenAI-compatible URL** (`agent/llm.py`, #66): with `OFFLINE=1` the local Ollama or LM Studio server at `LOCAL_LLM_BASE_URL`, online OpenRouter when `OPENROUTER_API_KEY` is set and the local server otherwise, so both setups stay in `.env` and `OFFLINE` switches (#230). The cloud model stays the default because local 8B models are unreliable at tool calling (`docs/data-plan.md` §6). Token usage comes back on every reply.
- **gpt-oss-20b answers locally, gpt-6-luna in the cloud** (#98). On the 28 from-memory questions gpt-6-luna passed 27 and added a fact from memory once, against 4 times for gpt-oss-20b, at $0.10 / $0.50 per million tokens and 5.8 s per answer; it was safe on all 49 safety messages. claude-haiku-5.5 at the same price added nothing but told the reader three times that Molecula has no data on stored drugs it never searched; deepseek-v4-flash answered from memory most ([chat model](../decisions/chat-model.md)). `LLM_MODEL` defaults to `openai/gpt-6-luna`. glm-4.7-flash, the only other downloaded model that fits the 24 GB GPU, added as much from memory as gpt-oss-20b, answered two to five times slower and ran past the time limits on 3 of 24 comparisons, so the local model stays gpt-oss-20b (#387).
- **A user may pick the model that writes the answers and the model that checks the messages** (#37, #363). The settings (bottom of the sidebar) list the configured model first as the default, then every model the local server lists (LM Studio lists what it has downloaded and loads one when it is first asked; embedding models are left out by name) and, online, `LLM_MODEL` and `LLM_MODELS` on OpenRouter. The list is read from the server on each `GET /models`, so the backend never takes a base URL or a key from the client, and `POST /chat` answers 422 for a name not on it; with `OFFLINE=1` no cloud model is listed. Above that list the settings offer **Model that checks the message**: the tested checkers `GET /models` lists, Jev online and LOCAL_LLM_MODEL (gpt-oss-20b) when a local server is set, and always "the model that writes the answer", sent as `checker: "decision" | "local" | "answer"`. The default is Jev online and gpt-oss-20b offline (`open_checkers` in `wiring.py`), and `POST /chat` answers 422 for a checker it doesn't offer, Jev offline for one. `ModelChoices` (`agent/choices.py`) builds a chat for each model and checker the first time it is asked for. With Jev, only the answering agent changes: Jev sorts the message and extracts the label filter, and the configured chat model (gpt-6-luna) checks the answer against its sources, because Jev only answers yes/no questions; so a model nobody measured never decides what is safe to answer, and the source check is an independent reader of its answer. With gpt-oss-20b or the answering model, that model runs all three checks (`open_chat_checked_by`), so a local pick checked locally asks no cloud chat model or Jev, which picking "my local model" suggests (the embedding model is set apart, by `EMBEDDING_MODEL`). When the answering model checks and is not a tested checker, the settings say the checks are unmeasured too: the safety check was measured only on gpt-oss-20b and Jev. Those chats need tools whose label filter their checking model extracts, so with `AGENT_TOOLS=mcp` each opens an MCP session of its own the first time it is picked (#380). Both choices are kept per browser, not per conversation. The settings mark gpt-oss-20b and gpt-6-luna as tested and say that every prompt and eval ran on gpt-oss-20b, with gpt-6-luna measured as the cloud model, so another model may do worse. A local model needs at least 32k tokens of context, as gpt-oss-20b is loaded with: in the PR's manual run, qwen3.8-27b's last call of a one-search answer to "How does imatinib work?" was 8,863 tokens, and LM Studio loads a model it is first asked for with its default load settings, 8,192 tokens and 4 parallel slots for gemma-4-12b-qat. The settings say so.
- **One decision-model client for LM Studio and OpenRouter, failing fast** (`agent/decisions.py`, #106). Jev on OpenRouter and decision models in LM Studio both speak TypeSafe's `/v1/systemone` ([API](https://docs.typesafe.ai/api)), so only the base URL changes, as for the chat model; LM Studio's OpenAI-style `/v1/decisions` uses other field names and isn't used. The client sends the question models from `schemas/decisions.py` and checks that every question got an answer of its own type. It doesn't retry and raises one of five errors (unreachable, timeout, model missing, request refused, bad response), which `GuardedChat` turns into the same refusal as a failed input check, so a message is never answered unchecked. A missing model looks different on each server, all recorded or documented: LM Studio answers 400 with `invalidModelIdentifier` (not downloaded or not a decision model), llama.cpp 501, OpenRouter 404 (also when a workspace guardrail blocks Jev). A downloaded model that isn't loaded is no error: LM Studio loads it on the first call, about 3 s for Kev-0.8B.
- **How long the model reasons is a setting, `LLM_REASONING_EFFORT`, empty by default.** LM Studio and OpenRouter both pass it on. Without it gpt-oss-20b in LM Studio reasons about as briefly as on "low" (12 to 58 reasoning tokens on a test question, 275 to 502 on "medium"), and gpt-5-mini on OpenRouter used 192 tokens, against 128 on "medium" and 64 on "low". On the no-label eval, medium and high didn't help gpt-oss-20b, and high left answers empty at the step limit ([no-label eval](../evals/no-label-2026-10-14.md), #198). The eval caches are keyed by the effort too. The documented local setup leaves it empty: on 28 questions about drugs with a label, medium added facts from memory to 6 answers against 4 and took 13.3 s against 9.3 s at the median, and the no-label controls went the other way, both within the spread between identical runs. So medium shows no gain there and costs time, also in the guard and the filter extraction, which use the same model ([answers from memory](../evals/from-memory-2026-10-14.md), #197). **The answers have their own setting, `ANSWER_REASONING_EFFORT`, medium unless set, and `LLM_REASONING_EFFORT` is left to the guard and the filter extraction.** On questions that combine a 3D view with a comparison or compare two drugs, gpt-oss-20b at its default effort stopped after the structure or the properties and wrote how the drugs work from memory; at medium every comparison searched both labels and the 3D answers compared the two structures from the tool data, for about 5 s more on a simple question and 7 to 13 s more on a comparison ([comparisons](../evals/comparisons-2026-10-17.md), #254). gpt-6-luna, the cloud model, answers as well at medium as at its own default and at the same cost, so medium is the default for the cloud answers too ([chat model](../decisions/chat-model.md), #256). The source check has its own setting, `SOURCE_CHECK_REASONING_EFFORT`, medium unless set, because it caught 10 of 17 cited additions at medium against 6 or 7 without (#212, #213).

## Tools and MCP

- **A tool answers with a result, never an exception.** Each tool returns a pydantic model from `schemas/tools.py`: the model reads it as JSON and the agent gets the typed result as the tool message's artifact, for the trace and the UI. A drug outside the store is `not_supported` with the suggestions, and in `compare_drugs` it is reported in its place while the others are compared. Arguments are checked like the API's (`DrugName`; 2–4 drugs to compare), and a bad one comes back as an `invalid_arguments` result with one line per problem, through LangChain's `handle_validation_error`, so the model can fix its call instead of the agent loop failing (#107).
- **A tool brings its own progress text and sources.** `build_tool` (`tools/base.py`) requires the status line the user reads while the call runs, and each result type in `schemas/tools.py` lists its own sources. The agent looks both up and knows no tool by name, so adding a tool means its module and one line in `agent/tool_registry.py`; a test fails if a registered tool has no progress text (#135).
- **The MCP server serves the agent's own tools, and the chat runs through it (`AGENT_TOOLS=mcp`, the default).** `mcp/server.py` turns each LangChain tool from `build_tools` into a FastMCP tool (`to_fastmcp` from `langchain-mcp-adapters`), so the docstring stays the one description and the argument model the one schema, and an MCP client gets the JSON the agent reads. A drug outside the store is a result; bad arguments or a failing tool are an error result, never a protocol error. With `AGENT_TOOLS=mcp` the backend reaches the same server through in-memory MCP sessions held for its lifetime, which proves the server end to end without a second process loading bge-m3 again. A chat whose label filter another model extracts (a picked model checked by gpt-oss-20b or by itself) gets a server and session of its own when it is first picked; `McpSessions` gives each session a task that opens, holds and closes it, because an anyio context must be left by the task that entered it, and closes them all at shutdown (#380). That server sends each tool's whole typed result as `structuredContent`, the label search's `retrieval` included, which the model never reads, and `tools_over_mcp` rebuilds it as the local tool's result type (kept on the tool by `build_tool`). So the chat's sources list, retrieval trace, reference numbers and the label-filter usage the daily cost limit and the dashboard count are the same as with local tools; a test runs one answer both ways and compares every event (#316). So `mcp` is the default since #380; `local` calls the tools directly. mcp is pinned below 2: 2.x renamed FastMCP, and `langchain-mcp-adapters` still needs 1.x (#42).
- **Outside MCP clients get reference numbers per session and the sources as `structuredContent`.** The chat numbers sources per answer in `NumberSources`, which an MCP client never passes through, so over `python -m molecula.mcp` every `ref` but the label passages' was null, and those restarted at 1 on each search. `build_server(number_sources=True)` serves each tool through a wrapper that calls it as a tool call (to keep the typed result), renumbers it with the calling session's `References`, and returns the same JSON text plus `structuredContent`: the result with its `sources()` added, so a client that reads only the structured part loses nothing. An MCP server can't tell where one answer ends, so the numbers climb over a long session but never change meaning. The chat's in-memory session (`AGENT_TOOLS=mcp`) numbers its sources per answer as with local tools, so its server sends the whole typed result unnumbered instead (#316); `References` moved to `schemas/tools.py` so `mcp/` needn't import the agent (#299).

## Answers and citations

- **The agent reports each step as a typed event, and the route only sends them.** `ChatAgent.stream` (`agent/agent.py`) runs LangChain's `create_agent`, and `AgentRun` (`agent/events.py`) turns its stream into the events in `schemas/chat.py`: `status`, `tool_call`, `tool_result`, `token`, `retrieval_trace` (one per label search, from the tool's artifact, with `filter_source` saying whether a model extracted the filter, Jev online and the chat model offline, or the agent named the drug), then `sources` (every source the tools returned, once) and `done` with the token usage of all model calls. So the endpoint, the tests and the evals see the same steps (#124). Text a model writes before it calls a tool ("I'll look up the labels.") stays in the stream, followed by a blank line, so the answer starts a paragraph of its own instead of running into it; it is kept rather than dropped because a model may start its answer there, and `run.answer`, which the citation check reads, stays the final message (#399).
- **Label passages are cited by number, and the agent hands out the numbers.** Asked for a Markdown DailyMed link, gpt-oss-20b wrote one that resolves in 38% of the 94 retrieval questions; in 53% it used its own `【4†source】` marker, which points at nothing (#125, [citations](../evals/citations-2026-10-13.md)). Each passage now carries `ref`, the model cites `[n]`, and each `Source` has the same `ref`, so the chat can turn `[n]` into a chip (#20). gpt-oss-20b then cites a passage in 96% of answers (the rest say the labels don't answer), and in 75 of 78 it cites the passage that holds the answer. About one answer in five writes the number in gpt-oss's own full-width brackets, `【1】`, so `cited_refs` reads both styles. That is a gpt-oss special case: qwen3.8-27b wrote `[n]` in every answer that cited, in every run, so a model that follows the prompt needs nothing extra. The numbers belong to one answer, not one search: the `NumberSources` middleware (`agent/references.py`) renumbers each tool result from a `References` counter passed as the run's context, before the model reads it. The counter, not the conversation state, decides the numbers because two searches in one model turn run at the same time and see the same state. A passage found twice keeps its first number. Numbers start at 1 again for each answer, and a number the answer cites that no source has is listed in the `sources` event's `unknown_refs`; the chat leaves it out (#129, #160). Since #207 every source is numbered, not only label passages: PubChem properties, ChEMBL targets and the reviewed PDB complex carry a `ref` too, keyed by their page's URL, and the chat shows them as chips named after the site ("PubChem · imatinib"). A prompt that makes the citation the permission to state a fact (#208) needs it: with only label passages numbered, gpt-oss-20b denied what `compare_drugs` returned in all 3 comparison controls of the no-label eval, said "no residue-level data" after `get_complex` returned the residues, and cited a number that points at nothing in 6 of the safety eval's 7 structure and property answers (2 of 7 with main's prompt).
- **The backend strips gpt-oss's channel markers from the answer as it streams.** gpt-oss writes in the harmony format, whose replies run on the channels `analysis`, `commentary` (tool calls) and `final`, and it sometimes writes `【commentary: get_complex】` where a citation would go (1 of 3 imatinib structure answers, #174). `AgentRun` passes the answer tokens through a `ChannelMarkerFilter` (`agent/channel_markers.py`), which holds back an open `【` and the spaces before it until the next chunks show whether it is a marker, because a marker arrives split over several chunks. A marker starts with a channel name and a citation with a digit, so `【1】`, `【1, 2】` and `[1]` pass unchanged. Stripping in the backend, not in the chat, keeps the marker out of what the source check reads and out of the earlier answers the frontend sends back; `to_langchain` strips earlier answers too.
- **Every result the model can cite starts with its `ref`** (`RefFirst` in `schemas/tools.py`, #166). With `ref` as the last field, a passage's number came 13 fields after its text, right before the next passage's text. In lists, gpt-oss-20b then handed out the numbers in order instead of by content, for example [6] to [10] down imatinib's warnings. With `ref` first, the wrong-passage citations in answers about several drugs, follow-ups and long lists halved: 32 → 16 of about 300 cited items, and the source check's `held_elsewhere` 20 → 8, over 60 answers each. The 94 single-drug questions are unchanged (every citation valid 0.99, the answering passage cited 75 → 76 of 79). A prompt sentence about citing list items added nothing, so the prompt is unchanged. Citing another drug's label, the other half of #166, no longer showed in 408 citations ([cited passages](../evals/cited-passages-2026-10-19.md)).
- **A local model gets the tool calls of the answer it is writing as one list of results after the question, not as calls** (`LocalChatOpenAI` in `agent/llm.py`, #277). gpt-oss-20b writes its reasoning before each tool call, and LM Studio drops it when the conversation goes back; after two calls with nothing before them, the model skipped reasoning and garbled its third call (6 of 60 answers in the cited-passages eval, up to 3 of them failing). Sending a line of reasoning back before each call stopped the garbling but doubled the wrong-passage citations in answers with several calls. The list of results after the question stopped it too, kept the citations at main's level (wrong passage 21 → 18 of about 300 items, in answers with several calls 13 → 9) and needed fewer calls, for about 4 s more per answer in those conversations and 2 s on single-drug questions, whose citations stayed the same ([reasoning before tool calls](../evals/tool-call-reasoning-2026-10-19.md)). OpenRouter models get the conversation as before.
- **A sentence about a drug needs a citation, or it is left out.** The system prompt (`prompts/agent/system.md`) is the owner's: the only facts about a drug are what the tools returned in this conversation; every sentence about a drug ends with the `ref` of the tool result it comes from, from any tool; a sentence that can't be cited is deleted; a partial answer says which part Molecula's data doesn't cover; a term may be explained in general but not with a fact about the drug; and each sentence is checked before sending. Every tool's docstring says its result carries a `ref`. Results without a `ref` (`not_supported`, `no_complex`, an empty `targets`, `drugs_without_label`) say what Molecula lacks, and the prompt lets the answer say so uncited. Measured with gpt-oss-20b, main's prompt → this one: answers from memory on 28 label questions 4 → 4, denials 1 → 0; metamizole answers that pass 13 → 14 of 24, the no-label controls 5 → 7 of 9 with no denial; cited numbers that point at nothing in the safety eval 3 → 0 of 49, safety itself unchanged (48 of 49, the miss is #169); on the 94 retrieval questions every citation is valid in 0.96 of answers either way, and the passage that answers is cited in 75 of 77 against 72 of 76. So it doesn't measurably cut what the model adds from memory, and two of the four additions cite a passage that doesn't hold them; that is the answer check's job (#205). It was adopted for the denials and the dangling references it fixes, and because a fact tied to one source is what that check compares against. With only label passages numbered, the same prompt denied what `compare_drugs` returned (13 of 24 metamizole answers denied data), so #207 came first ([from memory](../evals/from-memory-2026-10-14.md), [no label](../evals/no-label-2026-10-14.md), [safety](../evals/safety.md), [citations](../evals/citations-2026-10-13.md), #208).
- **The last step a request may take has no tools.** `create_agent`'s own model-call limit ends the answer with "Model call limits exceeded: run limit (6/6)". Instead the `StepLimit` middleware makes the last allowed call without tools and with `prompts/agent/step_limit.md`, which asks the model to answer from what it found and say what it couldn't look up; a tool call the model writes anyway is dropped. `done` says when the limit was reached (#124). A model that spends that last call on a tool call anyway is left with no answer text, which gpt-oss-20b did in 3 of 33 answers at reasoning effort high; an answer without text, at the limit or before it, ends with an `error` event ("Molecula couldn't finish this answer. Ask again, or ask a narrower question.") instead of an empty `done`, so the chat shows why and the source check doesn't run on nothing (#199).

## The chat route

- **`POST /chat` takes the conversation as text and streams server-sent events.** Each event is named by its `type`, its data is the event as JSON, and the stream ends with `done` or `error`. Once the stream has started the status code is sent, so an unexpected failure is logged and reported as a generic `error` event rather than cutting the stream. Plain `StreamingResponse`, no SSE library. Earlier turns arrive as question and answer text only, so their label passages and tool results never come back into the context; a request holds at most 10 messages, ending with the user's, and the frontend sends the latest ones. A question may have 4,000 characters and an answer 8,000, so a long answer the server wrote never gets a conversation refused (the longest in the first manual run was 2,308) (#125). A request that breaks a rule, or a message with control characters, gets a 422 whose `detail` is one sentence the chat shows as it is, with the field-level list in `errors`; every route answers a 422 this way (`guard/validation.py`; the control-character rule is `schemas/text.py`, #147).
- **A missing chat model turns the chat off; it doesn't stop the app.** The data routes and the drugs page need no model, and a `.env` with a key but no `LLM_MODEL` would otherwise keep Docker from starting. The startup log says why, and `POST /chat` answers 503 "Chat is off" (#125).
- **A failing chat model ends the answer with a readable `error` event.** Provider errors (timeout, no connection, rate limit, a refused key, an unknown model, a request too long for the context) and the per-request timeout each get a sentence for the user; the steps already sent stay. Other exceptions are bugs and are not caught here (#124).
- **Every answer reports its tokens and cost, split by step, and "unknown" is never 0** (#38). OpenRouter returns `cost` (US dollars) in the usage of every response, in the last chunk when streaming ([usage accounting](https://openrouter.ai/docs/use-cases/usage-accounting), checked 2026-10-19); Jev's `/v1/systemone` sends it too (`tests/fixtures/decisions/openrouter/answers.json`). LangChain 1.7 keeps that usage for structured output (input check, filter extraction, source check) but drops it from the last chunk of a plain stream (the agent's answer), so `PricedChatOpenAI` (`agent/llm.py`) copies it into `response_metadata["token_usage"]` there too, and `usage_of` (`schemas/usage.py`) reads every call the same way. OpenRouter also repeats `"role": "assistant"` in every streamed chunk, which leaves a structured call's `usage_metadata` empty, so `usage_of` falls back to the provider's own usage there (recorded in `tests/fixtures/openrouter/`). A local server costs 0 (`LocalChatOpenAI`, LM Studio's decision model); a call that reports no usage or no cost makes the sum `null`, which the chat shows as "unknown". `done` carries `usage_by_step` (`input_check`, `answer`, `label_filter`, `source_check`) and their sum as `usage`; the filter extraction runs inside `search_labels`, so its usage travels on the tool's artifact as `LabelFilter.extraction_usage`. The chat shows a line under each answer and the chat's total in the header (not on phones). An answer that fails or that the reader stops sends no `done`, so what its calls used isn't counted.
