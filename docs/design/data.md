# Data and the store

How the store is built, kept and downloaded, and how the sources are called. Each choice says what was picked and why, with the issue and the evidence. The short version is under "Key design choices" in [Architecture](../architecture.md#key-design-choices).

## The store

- **The store is the supported set, built ahead of time.** No live fallback: a live lookup brings no label, targets or reviewed complex, and can answer about the wrong drug ([local store](../decisions/local-store.md), #30).
- **Why SQLite.** One file and no database server: `data/build/molecula.db` can be copied, mounted into Docker and published as a snapshot (#35). The schema is versioned with `PRAGMA user_version`, migrations in `store/schema.py` upgrade a store in place, and a store from newer code is refused (#24, #34). The raw HTTP cache is a table in the same file (#24); the snapshot leaves it out (#35).
- **The app's stores share one SQLite connection and one lock** (`StoreConnection` in `store/db.py`, #389). FastAPI's thread pool and the agent's parallel tool calls use the connection from several threads at once. With a lock per store, two stores' queries could run at the same time, and they deadlocked: a query that calls the Python `casefold` function waits for the GIL while holding SQLite's connection mutex, and another store's thread reading its rows waits for that mutex while holding the GIL. It happened on 2 of about 60 answers in #256's comparisons eval, and within 2 s in a loop over the built store. With one lock per connection, store reads queue for each other, which costs little: in the same loop a `find` over the built store took about 1 ms and a target lookup 0.1 ms.
- **A fresh clone downloads the store from a GitHub release, and the embedding model from Hugging Face.** Building the store takes minutes and can hit NCBI's block, committing it puts growing binary data into git, and Git LFS counts every clone against its quota. The model can't go in the release: bge-m3's weights are one 2.27 GB file, and a release asset must be under 2 GiB. The archive's `molecula.db` keeps the `http_cache` table but no rows, so no raw response is published and an ingest step still runs on it. The manifest names the index's embedding model, and its `last_run` says since when the labels are known to be current: the start of the last label update that checked every drug, else the oldest label fetch (#35, #117, #118, `docs/data-plan.md` §4).
- **`ingest fetch` is a one-shot step with its own download code** (`ingest/fetch.py`, #118). It uses a plain streaming `httpx2` client, not the `SourceClient`: GitHub isn't a source, its download redirects to another host, and the `SourceClient` would cache the whole archive (88.6 MB) in `http_cache`. Docker runs it as the one-shot `fetch` service, which the backend waits for, not as part of the backend's startup, so the healthcheck isn't held up by a 2.3 GB download. Its downloads of the store and the model ignore `OFFLINE`: the data has to come from the internet once, and after that the app runs with `OFFLINE=1`. Building a cloud model's index does need `OFFLINE=0`, and `OFFLINE=1` also stops the other ingest steps' source calls and the label update. The model is pinned to a commit and its weights to a SHA-256, because Hugging Face checks only a download's size, and the app loads it by that commit: `snapshot_download` writes no `refs/main`, and without the revision the cached model doesn't load offline (`docs/data-plan.md` §4).

## Sources

- **One `SourceClient` for every source** (`sources/http.py`, #24): per-source rate limits, retries on 429, 503 and connection errors with `Retry-After`, a response cache in the store, typed errors, and `OFFLINE=1`, which raises before any request. An unknown host is refused, so a new source is added on purpose. 404s are cached too, so "no 3D conformer" stays known offline (#34); a body that fails to parse is dropped from the cache, so a GraphQL error sent as HTTP 200 doesn't stick (#75).
- **The openFDA key goes in the `X-Api-Key` header**, not the `api_key` parameter. In the URL it would end up in the cache key, the stored URL, retry warnings, httpx's log and exception text; a live 403 printed it (#67).
- **PubChem first, RDKit only fills gaps.** Displayed properties come from PubChem because they can be cited; RDKit's values differ by design (imatinib logP: Crippen 4.59, XLogP3 3.5). RDKit only generates a conformer PubChem lacks, for molecules up to 100 heavy atoms, and `conformer_source` records which (#34, [spike](../spikes/data-check/report.md)).
- **ChEMBL mechanisms through the parent ID.** Mechanisms hang on the salt form, so they are asked for by `parent_molecule_chembl_id`. The molecule is picked by exact InChIKey, then connectivity block, then name, and unnamed records are never picked: the exact match for glimepiride and tramadol has no mechanisms (#60, #70).
- **Interactions come from label text, with no safe/unsafe verdict.** There is no free structured interaction database: RxNav's API was shut down in January 2024 and DrugBank needs a licence (`docs/data-plan.md` §1).

## Labels

- **One canonical label per drug and product type**, on the drug's most common route: text-hash dedup kept 20 of 22 imatinib labels apart, and without the route rule ibuprofen got the IV label ([drug labels](../decisions/drug-labels.md)). It keeps the clinical sections and, since #92, the ones users ask about most: pregnancy and other specific populations, patient leaflets, dosage forms and inactive ingredients, abuse and dependence, clinical studies. The preclinical sections are never stored. Dosing, specific populations, patient leaflets, abuse and `overdosage` are stored with `sensitive = true`: overdosage says how an overdose shows and is treated, which matters offline, and answers about it put emergency help first (#63, #92, #17, `docs/data-plan.md` §5.5).
- **A label update follows the label chosen for each drug** (#341). Two count queries over the stored labels find those openFDA withdrew or published a new version of, and only those drugs are fetched again, selected again and re-indexed; one more count reads openFDA's data date first, so a run ends after one request when nothing was published. A window on the effective date, the plan in #25, has to reach back weeks because openFDA publishes labels late, and with 60 days it marked 110 of 133 drugs, about 1.85 GB to fetch again. A label from another manufacturer that the selection would now prefer comes only with `ingest labels`. A changed drug is re-indexed before its label rows are replaced, so a run that stops in between is repeated by the next; the store uses write-ahead logging so reads don't wait for it ([label update](../decisions/label-update.md)).
- **The backend runs the label update itself, every night at `LABEL_UPDATE_HOUR` (UTC, default 3)** (#342). It runs in the backend's process because Chroma lets one process write to the index, and with the index and bge-m3 the backend already holds, so a run loads no second 2.3 GB copy of the model and the next search sees the new chunks. A separate updater service was considered and dropped for the same reasons: it would hold its own model and need either the backend restarted after each run or Chroma as a server. The run gets its own SQLite connection: the app's reads go on over theirs and see each drug's labels before or after the change, never half of it. It runs in a thread, one at a time (`services/label_updates.py`), so the app keeps answering; a night whose run finds one still going is skipped. `LABEL_UPDATE_SCHEDULE=0` turns the schedule off, e.g. on a store kept as the eval baseline, and with `OFFLINE=1` or without a built store and index there is none. The dashboard's Update now button is behind `LABEL_UPDATE_BUTTON` (default off), which switches off `POST /labels/update` too, so nobody starts a run with a plain request. A run cut short by a restart is safe, since a drug is re-indexed before its labels are saved (#341). Drug names are read from the store on every call, label brands included, both for a name typed on its own and for the pattern that finds drug names inside a sentence (`CompoundService._mention_index`), so a brand a new label brings is found at once and a dropped one is no longer a mention. The pattern used to be built once per process, and a dropped brand still matched it but had no stored spelling, which ended the chat turn with a `KeyError`. Rebuilding it each time costs about a millisecond on the built store, less than the repeated reads it replaced (#418).
- **Every supported drug has a US label.** Metamizole, the only stored drug without one, was removed (#196). On gpt-oss-20b, no prompt or tool change made its answers good: each traded "Molecula has no data on it" for "it is a painkiller" from memory, and comparisons with it often searched only metamizole (#193, #200). The code still handles a drug without a label ([drugs without a label](../decisions/drugs-without-label.md), [no-label eval](../evals/no-label-2026-10-14.md)).
