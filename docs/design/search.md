# Label search

How the label text is indexed, filtered and ranked, and what was measured and left out. Each choice says what was picked and why, with the issue and the evidence. The short version is under "Key design choices" in [Architecture](../architecture.md#key-design-choices).

## The index

- **One chunking for every embedding model.** Chunks are 500 tokens of the bge tokenizer with 50 overlap, split per section, so a model comparison compares only the models and no chunk is cut off by a 512-token model (#87).
- **Repeated label text is indexed once, within its section group.** `clinical_pharmacology` repeats `mechanism_of_action` on 111 of 115 Rx labels; that text stays only under the specific section. OTC `warnings` repeats the consumer sections, but those are another group, and retrieval filters on the group, so both stay (#87, `docs/data-plan.md` §5.5).
- **bge-m3 embeds the labels, on the CPU.** In a comparison of 14 models on 94 questions it found the answering passage in the top 5 for 85% (bge-small: 80%), tied with the best CPU-sized models, in 37 ms per question, and it is multilingual for German questions (#46). GPU and cloud models reach 97–98%. The cost is 2.3 GB of weights ([embeddings](../decisions/embeddings.md), #88).
- **A server too small for bge-m3 embeds with gemini-embedding-2, with no section boost.** The deployed app's VPS can't hold bge-m3 and embed with it on its CPUs, so the cloud setup sets `EMBEDDING_MODEL=google/gemini-embedding-2` (OpenRouter), and a cloud model's boost defaults to 0 (`Settings.section_group_boost`; `RETRIEVAL_SECTION_GROUP_BOOST` still overrides it): under gpt-oss-20b's extracted filters it finds the answering passage in the top 5 for 98% of the 94 questions, against 91% for bge-m3 with its boost, and the boost only cost Gemini recall (0.91 at 0.15). It was the best or tied of the three cloud models on every measure, for 19 cents more per index build than text-embedding-3-large ($0.56). Each model has its own index: bge-m3's keeps the path releases unpack to, a cloud model's goes to `data/build/index/cloud/<model>/`, stays out of the release, and is built by `ingest fetch` once (170 s) or copied from a machine that built it. `OFFLINE=1` refuses a cloud model, and its key makes the default chat model the cloud one; a local model picked from the list (#37) still searches with the instance's cloud embeddings ([embeddings](../decisions/embeddings.md), #96). The benchmark page reads the setup from `GET /retrieval` instead of assuming bge-m3: the route reports what the settings name, so it answers also while the chat or the index is off, and the benchmark page marks the instance's model as the app's, matched on the model id the run file records. Until the backend answers, or when it doesn't, the page shows the local setup. The Flow tab reads the boost from each search's trace, so with boost 0 its ranking step reads "Keep the top N" and draws the bars without a bonus, and the guide keeps its recorded bge-m3 example with one sentence on the cloud setup's numbers (#350).
- **The index is tied to its embedding model.** The collection records the model, and querying with another one is refused: vectors of two models don't compare, and the query would fail on the dimension or quietly find nonsense. The weights are saved in `data/build/models/`, Chroma's own default embedder (an ONNX download) is off, and so is its telemetry, so `OFFLINE=1` makes no call (#87).
- **The label search is built at startup, and an index from another embedding model stops it.** The lifespan checks the model the index records before it loads bge-m3, so a mismatch fails at once, not on the first question. Startup with bge-m3 takes 6 s here on the GPU or the CPU, and the Docker backend is healthy after 7 s with `OFFLINE=1`. Without an index folder or a configured chat model the label search and the chat are off and the data routes still start; the folder isn't created, like the store (#108).

## Filter and ranking

- **The search is filtered to the drug and ranked by the part of the label.** The chat model extracts drug names, section groups and a product type (`prompts/rag/extract_filters.md`); the code resolves the names against the store and drops unknown groups, so a filter value the model invents never reaches the search. With the answer key's filters, bge-m3's recall@5 on the 94 retrieval questions goes from 0.74 over the whole index (0.76 with the exact search in #88; Chroma's HNSW search is approximate and misses one question) to 0.85 within the drug and, as a hard filter, 0.98 within the drug and section group. But gpt-oss-20b picks a wrong group for 20 of the 94 questions, and as a hard filter a wrong group hid the answer (recall@5 0.35 on those). So the drug filter stays hard and the groups only rank: the search takes the closest chunks of the drug's labels in the groups and in every section, and a chunk in a group counts `RETRIEVAL_SECTION_GROUP_BOOST` (0.15) higher in cosine similarity. With the extracted filter recall@5 goes from 0.84 to 0.91 (wrong group 0.35 → 0.70), and the answer key's ceiling drops by one question to 0.97 (`python -m evals.retrieval.filters`). 0.15 is the smallest boost that keeps the ceiling within one question; reciprocal rank fusion lost two ([filter extraction](../evals/chat-model-filters-2026-10-12.md), #98, #112). A question that names only unsupported drugs finds nothing instead of another drug's text (#13).
- **A label's brand is a name of its drug, and so is an unknown product name with one drug in it.** "Doryx MPC" or "Xhance" are brands of stored labels but not scope aliases, and "Fleqsuvy baclofen" names baclofen. With both, gpt-oss-20b's filter names the right drug for all 94 questions (was 88) and recall@5 goes from 0.78 to 0.84. A name with two drugs in it stays unknown, and a drug the name says the product lacks ("Non-Aspirin", "aspirin free") doesn't count. The rule lives in `CompoundService.resolve`, so `resolve_drug` and the other tools read a name as the label search does: "Voltaren arthritis gel" used to be diclofenac in `search_labels` but not supported in `resolve_drug`, and the local models told the reader so (#400). The question itself goes to the search unchanged: replacing brands with the generic name lowered recall@5 from 0.85 to 0.81 within the drug ([filter extraction](../evals/chat-model-filters-2026-10-12.md), #14).
- **A brand narrows the search to that brand's label, and a label without the section widens it again.** Diclofenac has the Voltaren gel (OTC) and Zipsor capsules (Rx), and only the gel's label answers "Can teenagers use Voltaren gel?" (#88). A label's brand counts only when it doesn't contain the generic name: openFDA brands like "good now omeprazole" or "DIPHENHYDRAMINE HYDROCHLORIDE" would otherwise narrow a generic or salt name to one label. But none of the 27 OTC labels has adverse reactions, pharmacology, interactions or contraindications, so "side effects of Advil" would find only the Drug Facts. When the labels the filter narrows to have none of the extracted section groups, the search takes every label of the named drugs and keeps them if one of those has the group, and the retrieval says what it gave up (#13, #112).
- **A search for several drugs searches each one and keeps 5 passages per drug.** One search over both drugs' labels returned the 5 best passages overall, and a drug whose label matched the question better took them all: "Compare ibuprofen and paracetamol" got 5 ibuprofen passages and none for acetaminophen, and the answer said Molecula has no data on paracetamol. Now each drug with a label is searched on its own (with its own section-group ranking and widening) and keeps its own `RETRIEVAL_TOP_K` best passages, the same as a search for that drug alone: 10 passages for two drugs. The owner chose 5 per drug over sharing 5 out (3 each), for the depth per drug, at the cost of a longer tool result for the model to read. On 12 two-drug searches with the filters built from the names, a drug got no passage in 5 before and in none after; single-drug searches are unchanged (retrieval eval identical) (#255).
- **`search_labels` asks a model for a filter only when the agent names no drug.** With `drug` set, the drug is checked against the store directly, which saves a model call per search (3.2 s with gpt-oss-20b); a question about two drugs leaves it empty and the filter is extracted. `section` joins the section groups either way, so it ranks and never hides a section. The shortcut costs recall when the agent leaves `section` out: the drug alone finds the answer in the top 5 for 0.85 of the 94 retrieval questions, the extracted filter for 0.91, and the drug with the right section for 0.97, so the tool description asks for both. The model reads the passages with their citation (DailyMed URL, section, label date, `sensitive`); the whole retrieval, with the filter, the widening and the dropped candidates, rides on the artifact for the trace (#16, #41) and stays out of the model's context. One search is 10–12k characters of JSON for five passages (#108).
- **Online, Jev fills the label filter; offline, gpt-oss-20b does** (owner's call, #287, #290). It runs when `search_labels` gets no `drug`, mostly for questions about two drugs. `open_filter_extractor` (`main.py`) picks `DecisionFirstFilterExtractor` (`agent/label_filter.py`) when the input check's decision model is set up, and it falls back to the chat model's extraction on any `DecisionModelError`, so a search never fails because of its filter. That is the default chat; in a chat whose checking model was picked from the list (#363), that model extracts the filter. `search_labels` stays a sync tool: LangChain runs it in a worker thread without an event loop, so the async Jev call runs there with `asyncio.run`. `DecisionFilterExtractor` (`rag/filters.py`) asks a yes/no per section group in one call and takes the groups at 0.5 or more, at most three; a decision model can't write a drug name, so `CompoundService.find_names` finds them in the question: scope names, aliases, label brands written with a capital first letter (some brands are ordinary words, "Stay Awake"), and words at a `difflib` ratio of 0.85 or more to one of them, which `resolve` answers with "did you mean" rather than taking them for the drug. On the 94 retrieval questions recall@5 is 0.90 against gpt-oss-20b's 0.91, in 0.27 s against 3.2 s; of 18 misspelled names, 17 come back "did you mean", where gpt-oss-20b corrected 9 itself. Jev set a product type on 68 of 94 questions that didn't say one, so it isn't asked for one; without that question recall@5 stays 0.90 at $0.0045 per 94 questions ([label filter](../evals/label-filter-decision-2026-10-19.md)). Both extractors share the store check, `FilterCheck`.

## Measured and left out

- **No query translation and no multi-query.** The question goes to the search as the agent writes it. Translating a German question to English found the answering passage for 3 more of 94 questions (recall@5 0.80 → 0.83 filtered to the drug; English 0.85) for about 4 s of gpt-oss-20b per search, and the agent already writes half its German searches in English; three rewrites merged by reciprocal rank fusion lost 5 (0.85 → 0.80) and put the model's memory into the search ([query translation](../evals/query-translation-2026-10-16.md), #114).
- **No hybrid search by default.** The search ranks by the embeddings alone (bge-m3 locally). BM25 next to it, merged by reciprocal rank fusion, returned the answering passage in the top 5 for 76 of the agent's 94 questions against 78: it rescued 8 whose answer was outside the section the agent asked for and lost 10, mostly ones bge-m3 ranked first, because fusion by rank drops how far ahead that passage was. On 8 questions about exact terms (CYP3A4, QT, eGFR) it brought 29 of 40 term-holding chunks against 26. The BM25 index is built with the vector index and shipped in the store, and `RETRIEVAL_MODE=hybrid` turns it on ([hybrid search](../decisions/hybrid-search.md), #44).
- **No score threshold.** `RETRIEVAL_MIN_SCORE` is 0, which drops nothing in practice: with bge-m3 the answering chunks score 0.43–0.78 and the best chunk that doesn't answer 0.44–0.75, so any cut drops answers too. Candidates below a threshold still go to the retrieval trace (#41). A re-ranker might give scores that separate (#13); #96 left it out, because it would run on the CPU too and so doesn't help the deployed server.
