# Running and deploying

Configuration, limits, login, the deployed setup and what is recorded. Each choice says what was picked and why, with the issue and the evidence. The short version is under "Key design choices" in [Architecture](../architecture.md#key-design-choices).

- **`.env.example` is filled in for a new machine and shows every other default** (#373). Its first block holds the few settings a clone sets, with working values: the OpenRouter key, `OFFLINE`, and gpt-oss-20b in LM Studio at `http://host.docker.internal:1234/v1`, the address a backend in Docker reaches the host's LM Studio by; without Docker it is `localhost`. Every other setting is a commented line with its default, so a copied `.env` changes nothing until a line is uncommented, and a test checks that each one names a `Settings` field once and that the value shown is the code's default. The reasons behind the defaults are in the docs the comments link to. With the local model filled in, a clone without a key sends its answers to LM Studio, so the backend logs at the start which model writes the answers and at which server.
- **`POST /chat` has a request limit per client and a daily cost limit, on by default** (#39). Per client IP, 10 questions a minute and 200 a day, over sliding windows; over the limit the route answers 429 with `Retry-After` and a sentence saying when to try again, before any model call, and the turned-away request isn't counted. The answers' cost from `done` (#38) adds up per UTC day; at `DAILY_COST_LIMIT_USD` ($2) the chat answers 503 with the wait until midnight UTC. A local chat model costs nothing, so it gets no cost limit (`chat_model_is_local`). Counters live in memory (`guard/limits.py`): one backend, reset on restart. The client IP is the peer address; `X-Forwarded-For` is read only with `TRUST_PROXY=1`, and then only its last entry, the one the proxy added, because a client can write the entries before it (uvicorn itself rewrites the peer address from a proxy on 127.0.0.1). Limits on by default so an instance is safe without setup (Danny's call); the evals that ask through `POST /chat` switch them off (`evals/no_limits.py`). Not counted: an answer that fails or that the reader stops sends no `done`, one the guard stops for repeating the system prompt counts only its input check (#203), and an unknown cost counts as 0 with a warning in the log; the request limit bounds both. At startup the log says which API keys are set, never their values.
- **A deployed app sits behind a Clerk login in Waitlist mode, on by setting the keys** (#343). Testers use the owner's OpenRouter key; asking each for their own key was dropped because it would sit in the browser and in every backend log line. Waitlist mode over an email allowlist: the allowlist needs a paid Clerk plan in production and lets nobody ask for access, while the waitlist lets a person ask and the owner approve them in the Clerk Dashboard, with no user table of our own. `ClerkLogin` (`api/login.py`) checks the `Authorization: Bearer` session token on every router but `/health` (the Docker healthcheck), with the instance's public key (`CLERK_JWT_KEY`) and no call to Clerk, so it works offline; `clerk-backend-api` was checked to make no request with `jwt_key` set (comment on #343). It accepts only session tokens, because the SDK checks an API key or machine token by calling Clerk, and only tokens issued for `CORS_ORIGINS` (`azp`): the deployed domain's root hosts another site, which could otherwise mint valid sessions. With the login on, the chat limits from #39 count per user (`user:<id>`), so testers behind one address don't share a limit; the usage log still records no user. The frontend fetches the token for each request (`fetchWithLogin`, Clerk's tokens live a minute and are cached until they near expiry), and `proxy.ts` sends a signed-out visitor to `/sign-in`; that is a convenience, the backend's check is the gate. Login off is a build without `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and a backend without `CLERK_JWT_KEY`: no Clerk code runs, the login pages answer 404, and development and evals are unchanged. The MCP server (`--profile mcp`) has no login and stays on localhost.
- **The deployed app runs from a compose file of its own, `docker-compose.coolify.yaml`** (#383). The owner's VPS runs Coolify, whose proxy routes each domain to a container and whose dashboard holds port 8000, so that file publishes no ports, leaves out the MCP server (no auth), keeps the store in a named volume (the checkout is cloned again on each deploy) and fixes `OFFLINE=0`, `TRUST_PROXY=1` (Coolify's proxy sets `X-Forwarded-For`) and gemini-embedding-2 by default, since the server can't hold bge-m3 (#96). The settings a deploy is likely to change (keys, models, limits, the label update's schedule, `LOG_LEVEL`) are each a `${VAR}` there, which Coolify shows as a field, empty for the code's default; the rest keep the code's default; the frontend's `NEXT_PUBLIC_API_URL` is required, because the browser reaches the backend at its own domain. App and API sit on two subdomains, with the app's origin in `CORS_ORIGINS`. The backend image creates `/data` owned by its user, so a new volume is writable. Coolify's build arguments are set to be managed in the Dockerfile, because by default it adds every variable as an `ARG` and the image history would hold the API keys; `CLERK_JWT_KEY` goes in on one line (the SDK strips line breaks anyway), because Coolify's multiline value reached the backend empty, which ran with the login off. `docker-compose.yaml` stays as it is for local use; a test keeps both files' services, builds and commands equal and checks each backend variable names a setting.
- **Each chat request is recorded in a usage log of its own, `data/runtime/usage.db`, with no question or answer text** (#334). One row per request: a random id, the time, the chat model, the outcome (`answered`, `error`, `stopped` when the reader leaves, `limited` when a limit turns it away), latency, tokens and cost from `done`, the names of the tools called, the guard's category, whether the step limit was reached and the error's `kind`, a field `ErrorEvent` gained for this. The same row goes to the log as one JSON line (`LOG_LEVEL`). Tool arguments and the client IP are left out too: arguments carry the drug names from the question, and medical questions are sensitive, while the metadata is enough for the dashboard (#335). The file lives outside `data/build/`, so `ingest export` never packs it and `ingest fetch --force` never replaces it, and it has its own table instead of the store's migrations (`store/usage.py`). `GET /stats?days=` (1 to 365 UTC days) sums it per day, with p50/p95 latency over answered requests (nearest rank, computed in Python: SQLite has no percentile), and counts the store's drugs, labels, sections, chunks, targets and structure files. Evals ask through the same route but record into a log in memory (`evals/no_limits.py`), so their runs don't show as use. A request the log can't store is only logged: recording never stops an answer. Not recorded: requests the input validation refuses (422) and those that reach the chat while it is off (503).
- **No question or answer text is stored on the server.** Conversations stay in the browser's IndexedDB (#243), and the usage log keeps only metadata (#334), because medical questions are sensitive (#36, #40).
